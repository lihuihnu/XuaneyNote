# XuaneyNote

**专注当下，记录生活。**

面向 Android 手机与平板的本地个人记录应用，将番茄钟、日记本、手账、笔记本和备忘录组织成一个连贯的使用体验，而不是五个互不相通的小工具。

> **项目状态：M0 / 规划基线，2026-10-17（Asia/Tokyo）。**
> 本次初始化只冻结项目目标、产品范围、技术方向、开发顺序和仓库规范。尚未实现 Android 工程、应用功能、APK、自动化工作流或性能验收。下文的性能数字均为待验证目标，不是实测成绩。
>
> 本文件是初始化阶段的唯一规划与治理基线。后续开发须先阅读本文件；如拆分到 `docs/`、`GOVERNANCE.md`、`AGENTS.md`，必须保持要求完整并更新入口，不能产生互相冲突的规范。

## 1. 项目目标与不可突破的边界

| 目标 | 明确含义 | 验收方向 |
| --- | --- | --- |
| 完全本地 | 核心功能不依赖服务器、账户、云同步或远程资源 | 首次安装后在飞行模式下完成核心闭环 |
| 免费、无需登录 | 不加入账户体系、广告、订阅、付费解锁或试用期限 | 打开即用；功能不设置收费门槛 |
| 操作丝滑 | 输入、滚动、切换、保存不被数据库和图片处理阻塞 | 在注明型号的真实设备上测量，而非只看模拟器 |
| 功能实用 | 优先完成记录、找回、提醒、专注、备份，而非堆装饰 | 每一阶段交付可实际使用的完整流程 |
| 界面美观 | 统一排版、配色、间距、动效和空状态 | 同时验收手机、平板、明暗主题和大字体 |
| 数据属于用户 | 本地可导出、可恢复、可迁移；删除含义明确 | 导出恢复往返一致，永久删除可验证 |
| 易于长期维护 | 少量清晰模块、可复现构建、必要测试与可追溯结果 | 源码 SHA、测试环境、结果和限制对应一致 |

**应用运行时边界：**不申请 `INTERNET` 或 `ACCESS_NETWORK_STATE`；不集成广告、埋点、远程崩溃上报、云字体、远程图片加载或后台更新检查。审核最终合并后的各发布变体 Manifest，不能只审核手写 Manifest。开发时下载 Android SDK/依赖不属于应用运行时联网。

默认不接入系统自动云备份；同时设计并验证适用 Android 版本的备份、设备迁移排除规则。不能把 `allowBackup=false` 当成所有厂商设备上绝对禁止迁移的充分证据。[R5]

用户主动调用系统分享或选择导出位置时，系统中可能存在第三方云存储提供者。界面应明确说明“由你选择目标，应用不自动上传”，并优先引导本地文件；不能声称应用能够控制第三方接收者或系统输入法。

## 2. 产品定位：统一记录，关联专注

核心使用流程：**快速记下一件事 → 整理为笔记或待办 → 开始一段专注 → 在日记或手账中回顾。**

笔记、日记、备忘录共享记录元数据、标签、附件、搜索与回收站能力。番茄记录可关联待办或笔记。手账复用记录和附件基础设施，但保留自己的页面结构，不能为了“统一”而把画布、计时器和所有业务都塞进一个巨大 JSON。

首次打开显示真实空状态和明确的创建入口。不把测试数据、示例日记、开发者项目或虚构的专注统计写进正式用户数据库。设计预览和自动测试只能使用隔离的合成数据。

### 2.1 页面结构

手机使用四个主要入口：

| 页面 | 核心内容 | 主要操作 |
| --- | --- | --- |
| 今日 | 今日待办、当前专注、最近记录、当天日记入口 | 快速记录、完成待办、继续专注 |
| 记录 | 笔记本、笔记、日记、备忘录；按类型筛选 | 新建、搜索、分类、编辑、归档 |
| 专注 | 番茄计时器、关联任务、本地历史与统计 | 开始、暂停、继续、结束 |
| 手账 | 日/周模板、手账本、页面列表 | 新建页面、排版、回顾、导出 |

搜索、设置、备份和回收站放在清晰的次级入口；不为了增加栏目把底部导航挤满。快速创建按当前页面提供合理默认值，避免每次先面对五种工具的选择题。

平板采用导航栏与“列表—详情/编辑”双栏布局，充分利用横向空间；窄窗口自动回到单栏。按窗口大小而非简单的“是否平板”判断布局，支持横竖屏、分屏和外接键盘，切换时保留当前编辑状态。[R2]

### 2.2 五项功能的 V1 边界

| 功能 | V1 应交付 | 明确后置 |
| --- | --- | --- |
| 番茄钟 | 可配置工作/短休息/长休息；暂停、继续、结束；关联待办；本地历史 | 在线排行榜、社交监督、复杂游戏化、常驻白噪声资源库 |
| 日记本 | 按日期浏览；一天允许多篇；文字、图片、可选心情；本地检索 | 自动定位、联网天气、AI 分析、社交发布 |
| 笔记本 | 笔记本分类、标签、置顶；文字及基础 Markdown；图片；自动保存 | 类 Notion 数据库、多级无限嵌套、协同编辑、插件系统 |
| 备忘录 | 快速记录、独立待办、到期时间、一次性本地提醒、完成状态 | 复杂重复规则、项目管理、外部日历双向同步 |
| 手账 | 日/周模板；文字、图片、分隔块；块排序和样式；本地页面与图片导出 | 无限画布、完整矢量编辑器、PDF 批注、低延迟手写引擎 |

**手账不是被取消，而是先做轻量排版版。** 触控笔、压感、套索、橡皮擦和手掌误触抑制作为 V1.1 独立能力验证，不与初版编辑器同时开工。

V1 不做 iOS、Web、桌面端、云同步、账号登录或内置 AI。跨设备迁移先通过用户主动导出/导入完成。

## 3. 视觉与交互规范

整体方向为“安静的纸面感 + 清晰的现代工具”：暖白或中性浅色背景、低饱和强调色、充足留白、可辨识层级。深色主题单独设计，不能仅把浅色反相。优先使用系统字体与随包提供的合法资源；不依赖网络取字体或模板。

采用 Material 3 组件和统一设计令牌，同时保留 XuaneyNote 自己的色彩、卡片、编辑器与专注页风格。初版不引入复杂毛玻璃、大面积实时模糊和持续播放的背景动画。

交互基线：

- 常用创建操作应在两次点击内到达；编辑页打开后可直接输入。
- 保存状态明确区分“保存中 / 已保存 / 保存失败”；只有数据库提交成功才显示“已保存”。
- 中文输入法组合输入、光标、选区、撤销与键盘遮挡是编辑器的正式验收项。
- 切换页面时保留合理的滚动和编辑位置；返回不能无声丢弃未保存内容。
- 动效建议控制在 150–250 ms，尊重系统减少动画设置；触感反馈可关闭。
- 可交互区域以至少 48 dp 为设计基线；同时检查 TalkBack、大字体、颜色对比和无障碍标签。

平板从 PR-A 就使用真实自适应布局，不等到手机版完成后再简单拉伸。所有截图使用合成数据并标注为设计预览或实际运行截图，不能混淆。

## 4. 技术路线

**推荐并采用的方向：原生 Kotlin + Jetpack Compose + Material 3 + Room + DataStore。**

当前目标只有 Android，并且强调编辑体验、系统提醒、平板适配与后续触控笔能力，因此不引入 Flutter/React Native 的跨端层，也不使用 WebView 承载核心界面。这是本项目的范围选择，不代表其他方案普遍性能较差。

| 层次 | 方案 | 约束 |
| --- | --- | --- |
| UI | Jetpack Compose、Material 3、官方自适应布局组件 | 状态驱动界面，尽量复用稳定组件 |
| 状态与并发 | ViewModel、StateFlow、Kotlin Coroutines | 单向数据流；界面不直接读写数据库 |
| 结构化数据 | Room / SQLite | 事务、索引、显式迁移；不允许破坏性迁移清空数据 |
| 设置 | DataStore | 保存主题、番茄偏好等小型配置，不存笔记正文和图片 |
| 文件与附件 | 应用私有文件目录、系统文件选择器 | 导入时复制到受控目录，不依赖临时 URI 永久可用 |
| 提醒 | AlarmManager、系统通知 | 明确权限与系统限制；不将 WorkManager 当作秒级计时器 |
| 可延迟维护 | 必要时使用 WorkManager | 仅做适合延迟的清理等工作，不常驻空转 |
| 依赖注入 | 先用显式构造器与小型应用容器 | 不为少量对象提前引入重型框架 |
| 构建 | Gradle Kotlin DSL、版本目录、适用时使用 KSP | 固定版本和校验值；避免动态版本及不必要的代码生成 |

官方文档支持 Compose 单向数据流、Room 本地结构化存储以及 DataStore 小型设置存储；本项目在此基础上采用尽量简单的分层。[R1][R3][R4]

最低版本暂定 **Android 8.0 / API 26**，作为减少兼容分支的初始产品取舍。PR-A 必须核对所选依赖的最低版本要求；`compileSdk`、`targetSdk`、JDK、AGP、Gradle、Kotlin 与 Compose 的具体稳定版本在 PR-A 联合验证后锁定，不在规划文档中编造“最新版本号”。[R11]

### 4.1 适度模块化

初期只创建四个实际需要的 Gradle 模块：

```text
:app                  应用入口、导航、依赖装配、feature 包
:core:model           纯 Kotlin 模型、计时状态与业务规则
:core:data            Room、DataStore、文件存储及仓库实现
:core:designsystem    主题、设计令牌、可复用 Compose 组件
```

`app` 依赖这些基础模块；`data` 依赖 `model`；`model` 不反向依赖 Android UI 或数据库。功能先在 `app` 内按包组织，达到真实规模或出现编译瓶颈后再拆分 feature 模块。基准测试模块也按实际需要新增。

复用此前编译优化经验：先测配置耗时、依赖下载、Kotlin 编译、资源处理和打包耗时，再决定优化点。避免一次创建大量空模块、重复执行相同 Gradle 任务，或为“架构完整”增加无实际用途的抽象。

## 5. 本地数据合同与可靠性

### 5.1 逻辑模型

下面是目标模型，不要求 PR-A 一次创建所有表。

| 实体 | 关键内容 | 规则 |
| --- | --- | --- |
| Notebook | ID、名称、排序、创建与修改时间 | 分类容器，不持有复制的正文 |
| Entry | ID、类型、标题、内容格式与版本、正文、笔记本、日期、归档/删除状态、修订号 | NOTE / DIARY / MEMO / JOURNAL 共用元数据 |
| Tag / EntryTag | 标签及关联 | 关系单独存储，便于筛选与清理 |
| Attachment / EntryAttachment | 相对路径、类型、大小、SHA-256、所属引用 | 大文件不塞进数据库正文 |
| Task | 标题、完成状态、可选 Entry 关联、到期时间 | 待办是实体，不反向解析 Markdown 勾选框作为唯一真相 |
| FocusSession | 关联任务/记录、阶段、运行片段、暂停状态、计划时长与累计时长 | 状态转换和统计结果可追溯，不重复计数 |
| Reminder | Entry 或 Task 目标、计划时间、时区/规则、调度状态 | 明确单一有效目标；使用约束防止悬空关联 |

所有实体使用本地生成的稳定 ID。时间点以 UTC 保存；日记同时保存用户选择的本地日期和相关时区信息。旅行或切换系统时区不能无声把既有日记挪到另一日。

笔记、日记和普通备忘录优先使用文本/Markdown 正文；手账使用有版本的页面结构。两者都显式记录 `body_format` 与 `body_version`，不能把格式转换当作普通字段修改。搜索文本为可重建派生数据，不作为唯一正文。

### 5.2 保存、搜索与删除

编辑输入先更新内存状态，通过串行、可合并的写入队列异步保存；目标为停止输入后约 300–500 ms 发起保存。需要最大等待时间或周期性草稿检查点，避免持续输入时永远不落盘。生命周期回调只能补充触发保存，不能作为崩溃安全的唯一机制。

已提交的修订必须在进程被终止后完整恢复。保存中的极短输入窗口必须真实呈现，不能承诺在任意断电瞬间绝对零丢字。存储空间不足、事务失败和附件复制失败需要可见错误，禁止先显示成功再悄悄丢弃数据。

搜索第一版保证中文连续关键词、英文、标签和类型筛选正确。先实现参数化的基础检索并测量万条记录，不把默认分词全文索引误当作已经解决中文检索。只有测量证明需要时，才引入分词或 n-gram 索引；原文永不因索引归一化而被改写。

删除进入回收站，提供恢复与明确的永久删除操作。V1 不默认定时永久删除用户内容。永久删除必须清理正文、索引、无引用附件和缩略图；共享附件按引用检查，不能误删其他记录使用的文件。数据库删除不等于可证明的闪存物理擦除，产品文案不得夸大。用户先前导出的外部备份不会被应用自动删除。

### 5.3 备份与恢复必须提前完成

在鼓励用户长期写真实内容之前，完成便携备份与恢复。不能把备份留到“功能都做好之后”。

备份合同至少包含：格式版本、应用/数据库版本、导出时间、记录与关联数据、附件清单、文件大小与 SHA-256。初版以结构化数据和附件为迁移合同，而不是把运行中的 SQLite 主文件直接复制一份。

导出必须取一致性快照，附件在导出过程中不能被并发永久删除。导入先校验版本、路径、大小、数量、哈希和引用完整性，再导入暂存区；全部验证通过后才切换或提交。失败时保留原有资料。覆盖恢复必须先明确提示并保留可恢复的原状态；合并导入按 ID/修订处理冲突，不静默覆盖。

测试必须覆盖空备份、多条记录、图片附件、重复导入、损坏文件、未知版本、路径穿越、解压大小超限、中断及空间不足。计时运行状态和系统提醒在恢复后重新确认，不能直接复活旧设备的“正在专注”状态或批量触发过期提醒。

便携备份的密码保护在 PR-B 明确选用经过审阅的成熟加密库/容器和格式，禁止自创密码算法。无密码导出必须警示明文风险。设备绑定的 Keystore 密钥不作为跨设备恢复的唯一解密凭据；密码遗失无云端找回。[R12]

**本地存储不等于额外的应用级加密。** Room 不是默认加密数据库；尚未实现和验证时不能宣称“加密日记”。可选生物识别应用锁与数据库加密是不同能力，需分别说明威胁模型、恢复方式和实际覆盖范围。

## 6. 番茄钟与提醒的特殊设计

默认可以提供 25 分钟专注、5 分钟短休息、15 分钟长休息的可修改预设；每四个完成的专注周期建议长休息。V1 默认由用户确认开始下一段，不在用户离开后自动累计一整天的“专注成绩”。

倒计时不能依赖后台每秒递减变量。同一次设备启动期间，使用包含休眠时间的单调时钟计算剩余时间；墙上时间用于展示和日期归属。保存阶段、累计有效运行时长、当前时钟基准和启动标识，显式处理设备重启。[R6]

需要验证的状态包括：开始、暂停、继续、正常完成、手动结束、进程重建、熄屏、设备重启、系统时间修改、跨日和权限撤销。状态转换应幂等，重复广播或重启不得生成重复完成记录。重启后标记中断并让用户确认，不能把关机时间自动算成已完成专注。

通知与准点提醒分开授权。只在用户启用相应功能时解释并请求必要权限；拒绝通知或精确闹钟权限后仍能记录、查看计时和使用其他功能。界面清晰说明“仅前台提示”或“提醒可能延迟”等真实能力，不假装权限已经获得。

精确提醒应检查平台能力、权限和当前分发政策；V1 优先评估用户授权的 `SCHEDULE_EXACT_ALARM` 路径，不默认声明适用范围更窄的 `USE_EXACT_ALARM`。WorkManager 不承担准点番茄提醒。不要伪装成媒体播放或数据同步前台服务来保活。[R6][R7]

**不承诺在用户强行停止应用、厂商拦截、关机或权限被撤销后仍必定准点响铃。** 这些边界必须通过测试记录与应用内说明交付，不能靠模拟器一次倒计时成功就宣称完成后台计时。

## 7. 开发里程碑与合并条件

不做全功能同时开工。以下阶段按顺序推进；每个阶段通过实际验收后再进入下一阶段，不给出未经工程验证的工期承诺。

| 阶段 | 交付范围 | 进入下一阶段的条件 |
| --- | --- | --- |
| M0：本次初始化 | 项目目标、范围、架构、数据原则、CI 与证据规范 | 文档实际进入仓库，状态表述真实 |

## 8. 质量门禁与性能目标

### 8.1 功能和数据门禁

| 门禁 | 最少覆盖 |
| --- | --- |
| 纯业务单元测试 | 计时状态机、日期归属、排序、统计、冲突规则 |
| 数据集成测试 | Room DAO、显式迁移、原子保存、索引、附件引用、删除 |
| 备份恢复 | 数据往返、哈希一致、损坏输入、取消/中断、原数据保护 |
| 界面测试 | 创建→编辑→保存→重开；搜索；手机/平板关键流程 |
| Android 行为 | 通知拒绝、闹钟拒绝、熄屏、进程重建、重启、时区与时间修改 |
| 隐私与供应链 | 最终 Manifest、权限、运行时网络依赖、日志、资源许可、密钥扫描 |
| 发布测试 | 安装、覆盖升级、版本迁移、签名身份与 APK 哈希 |

模拟器负责可重复的功能门禁；真实手机和平板负责触摸、输入法、功耗、厂商后台行为和真实性能。没有真机证据时，报告必须写“待真机验收”，不能把模拟器帧率写成真机性能。[R8]

### 8.2 初始性能预算（全部待测）

以一台记录清楚型号、系统、刷新率和运行条件的中档 Android 手机为基线，使用 release/profileable 构建与固定的合成资料集；平板另做对应基线。

| 指标 | 初始目标 | 测量方式 |
| --- | --- | --- |
| 冷启动到可操作首页 | P95 ≤ 1.5 s | 固定设备至少 30 次，区分冷/温启动 |
| 常用列表打开 | P95 ≤ 200 ms | 已有 10,000 条记录，不含首次图片解码 |
| 本地关键词搜索 | P95 ≤ 300 ms | 10,000 条、平均约 2 KiB 的固定中英文文本 |
| 常见滚动与切换 | 60 Hz 基线下卡顿帧比例 < 1% | Macrobenchmark/FrameTiming，记录场景与重复次数 |
| 编辑可见反馈 | P95 ≤ 50 ms | 输入到界面更新，数据库写入不阻塞主线程 |
| 文本编辑常态内存 | 目标 PSS ≤ 200 MiB | 定义场景、重复次数，图片/手账场景单列 |
| V1 发布 APK | 初始目标 ≤ 30 MiB | 记录实际分发 APK 字节数与包含资源 |

预算是发现问题的工具，不是为了过关随意改阈值。首次基线可发现目标不合理；任何调整都需记录设备、数据、原因和实测证据。高刷新率设备另按实际帧预算评估，不能用 60 Hz 阈值冒充 120 Hz 验收。

性能手段按证据引入：分页/增量加载、缩略图、稳定列表键、后台 I/O、控制重组范围；确认收益后再引入 Baseline Profiles 等优化。禁止在尚未实现数据可靠性时优先进行复杂微优化。

## 9. GitHub 开发与 Agent 执行约定

复用既有项目的有效经验，但**不复制其他项目的私有代码、数据、服务器配置、访问地址或密钥，也不继承自托管 Runner 策略**。

1. **先读实际远端。** 开工前核对仓库、最新 `main`、活动 PR 和 HEAD，不根据聊天中的旧 SHA 直接改代码。
2. **主线串行开发。** 维护者和 Agent 同时只推进一个活动开发 PR；在当前 PR 续做、验收、合并后再开下一个。公开仓库的外部贡献可以存在，但纳入主线时仍需顺序审阅。
3. **初始化之外走 PR。** 本次空仓库初始化可直接提交默认分支；后续功能、修复和治理修改原则上通过独立分支与 PR，不越过已有保护规则。
4. **冻结范围与合同。** 一个 PR 解决一个清晰阶段，不同时重写 UI、存储格式、计时器和 CI。数据格式和迁移改变需要显式说明。
5. **只认可最终版本证据。** 记录 PR HEAD 与实际被测试的 SHA；发生新提交或合并冲突修复后，旧 SHA 的通过不能冒充新版本通过。
6. **先复现再修复。** 保留失败证据，做最小针对性复现；不通过延长超时、隐藏错误或删除失败断言把红灯变绿。
7. **清晰报告状态。** 区分“已规划、已编码、已提交、已触发、排队、运行中、通过、已归档、已合并、已发布”。未测试的内容明确标注。
8. **长任务交接。** 提交必要的长 Runner job 后，确认工作流、run ID、源码 SHA 和状态，结束当轮回复，由用户监控并告知“CI 已结束”；不持续轮询，不宣称会在后台等待。
9. **简洁可维护。** 类型和职责清晰，关键计时、存储、迁移逻辑写必要中文注释；避免巨型文件、无意义包装和提前设计插件系统。
10. **清理有边界。** 清理临时文件与已确认合并的自有开发分支；不可删除用户资料、未合并工作、历史证据标签或签名密钥。

如当前连接器不能触发某种工作流，应使用实际可用且已验证的触发路径并说明，不能把“写了 YAML”说成“已开始执行”。需要用户操作时，只说明真实缺口，不重复索要已知信息。

## 10. 官方 Runner 与精简 CI 策略

### 10.1 执行环境与触发原则

**本项目只使用标准 GitHub-hosted Runner。** 初始 Linux 标签采用 `ubuntu-24.04`，这是 GitHub 官方托管环境，不是此前项目的 Ubuntu26 自有服务器。不配置 self-hosted，不使用腾讯云，不设置三级回退，也不启用付费 larger runner。

GitHub 官方当前对公开仓库的标准托管 Runner 提供免费使用，但这不等于任意存储、缓存或下载链路都没有限制。本项目按有配额的前提设计，不依赖 Actions Artifact 交付结果。[R9][R10]

PR-A 建立单一普通 CI 入口。PR 更新运行一次必要门禁；保留显式手动重跑入口，但不叠加分支 push、PR、评论和定时器重复构建同一版本。文档修改只跑文档/治理检查，不下载 Android SDK 或启动模拟器。

根据路径分类安排单元测试、Lint、构建与必要的设备测试。路径分类在工作流内部完成，确保最终汇总检查给出明确结论，而非因为整条工作流被跳过导致必需检查长期 pending。

同一 PR 新提交取消旧验证；固定超时，小规模设备矩阵，优先重跑失败 job。模拟器矩阵与长性能回归只在相关修改或显式验收时运行；不每次文档提交都启动全平台测试。合并后的发布验证针对实际发布 SHA，不借用不同 SHA 的旧结果。

### 10.2 不依赖 Artifact 的证据交付

**结果、日志和必要资源直接在当前仓库留存；不把 Actions Artifact 当作唯一或默认交付渠道。** 默认不使用 `actions/upload-artifact`、`actions/download-artifact`，不自动引入 Git LFS 或外部对象存储。

| 内容 | 保存方式 | 约束 |
| --- | --- | --- |
| 产品规划、源码、人工资源与小型测试夹具 | `main` 中的正常受审阅文件 | 资源注明来源/许可，夹具只能是合成数据 |
| 测试结果与必要诊断日志 | 同仓库、独立不可覆盖的 evidence 标签 | 结果提交不混入生产 `main`，不反向触发构建 |
| 性能报告与少量验收截图 | evidence 标签内的 JSON/CSV/Markdown/图片 | 对应确切源码与设备；保留足够复核的数据 |
| 已验收、待分发的 APK | 同仓库的独立版本交付标签，连同清单与哈希 | 只保留实际发布版本，不提交每次 CI 的 APK |
| Gradle/SDK 缓存、编译目录、模拟器数据、临时 APK | Runner 临时目录 | 使用结束后清理，不提交仓库 |

建议证据引用格式：`evidence/run-<run_id>-attempt-<attempt>-<source_sha12>`。证据目录至少包含：

```text
evidence/
  manifest.json        完整源码 SHA、tested SHA、run/attempt、命令、工具链、设备、结论
  summary.md           成功/失败/未执行的清单和限制
  results.json         可机器检查的原始统计或测试摘要
  logs/                已检查并脱敏的必要文本日志
  checksums.sha256     所有载荷文件的字节哈希，不包含清单自身
```

PR 使用合并引用测试时，`source_sha` 与 `tested_sha` 必须分别记录。截图、配置、原始结果与摘要需要互相一致；不能只有“PASS”而没有可复核依据。

构建成功与证据写入成功是两个独立状态。归档后从远端重新读取并校验文件身份与哈希，才算交付完成。上传失败不能被构建成功掩盖；取消/超时任务只能保留实际取得的部分证据，不补造完整报告。

证据默认追加且引用不可覆盖；不 force-push 覆盖旧证据，不为减少表面文件数量擅自删除证据标签。历史追溯与存储预算发生冲突时，提出明确方案另行审阅。

### 10.3 公开仓库的写权限隔离

普通构建与外部 fork PR 只授予必要的只读权限，不接触签名密钥和写仓库凭据。提交的源码、测试输出、PR 标题和日志都按不可信输入处理。

归档需要独立的受信任发布步骤或维护者通过连接器执行。自动化发布程序必须来自受保护的默认分支，仅按允许的 run/SHA 读取小型结果和日志并作为数据处理；不能执行待归档分支的脚本，不能把日志插入 shell 执行。第一版未完成该隔离前，采用维护者核验后经连接器写入证据的路径，不仓促给整个测试 job `contents: write`。

不使用 `pull_request_target` 检出并执行外部 PR 来换取写权限；也不能用 `workflow_run` 绕过同样的信任边界。Action 固定经过核验的完整提交 SHA；工作流、依赖升级和签名路径须重点审阅。公开测试只用合成内容，不上传真实日记、手机备份、私钥或令牌。[R13]

PR-A 的 CI 验收同时包含一次成功结果和一次受控失败结果的仓库证据交付演练；未验证归档读取链路前，不宣称“结果均已可下载”。

### 10.4 容量预算与清理顺序

以下是项目预算，不是对 GitHub 服务额度的承诺：

- 单份日常文本日志目标不超过 2 MiB；单次常规证据总量目标不超过 10 MiB。优先降低无意义日志量。确需截断时记录原始字节数、截断位置和 `truncated` 标志，不称其为完整原始日志。
- 普通图片/资源单文件目标不超过 2 MiB；发布 APK 目标不超过 30 MiB。超出预算先审阅用途与分发策略，不拆片规避限制。
- V1 前监控仓库完整历史大小，250 MiB 作为初始预警线。GitHub 对普通 Git 文件和仓库规模有额外建议/限制；**从工作树删除文件不会自动清除 Git 历史体积**。[R10]
- 默认不启用 Actions 持久缓存；同一 job 内可复用已下载依赖。只有冷/热构建测量证明收益且明确缓存预算后，才通过单独审阅启用有界缓存。SDK 镜像和模拟器镜像不能作为普通资源提交。

清理顺序：**收集必要结果 → 检查敏感信息与容量 → 写入并从远端核验 → 清理 job 临时产物。** 失败路径也尽量保存受限诊断再清理；若 Runner 被强制终止，报告实际能恢复的证据边界。

清理只针对当前 job 创建的已知目录，路径需校验，使用 `always()` 或等效收尾机制；不得对未知目录执行宽泛的递归删除。Gradle Wrapper 等经审阅的必要构建引导文件与自动生成的 `build/` 产物要区分，不能一律删除。

## 11. 发布、许可与安全说明

每个发布包关联确切源码 SHA、版本号、构建工具链、APK SHA-256 与签名证书指纹。签名身份必须跨版本保持可更新；正式签名密钥只进入受保护的机密存储，绝不写入公开仓库或证据。普通 PR 不生成带正式密钥的包。

本项目的“免费使用”目标已经确定；**源代码许可证尚待维护者确认**。公开仓库不等于已授予任意再分发许可，本次不擅自替维护者添加不可逆的许可证承诺。正式公开发行前，确定 `LICENSE`，并审核依赖、图标、模板、声音和字体的许可及署名要求。[R14]

问题反馈应使用合成示例和经过裁剪的脱敏日志；不要求用户在公开 Issue 上传完整笔记库。发现敏感内容或密钥泄露时先限制传播并轮换凭据，普通删除提交不能等同于从公开历史中消除泄露。
